# Org storage is the source of truth for shared skills

A skill shared across agents lives ONCE, at the org/workspace level: `ws/<org>/shared/skills/<slug>/…` in the cloud bucket (under the existing `OrgRoot` seam, beside agent prefixes) and `~/.houston/workspaces/<Workspace>/.shared/skills/<slug>/…` on desktop. Clients read and write that source directly (gateway routes `/v1/orgs/:org/skills…` in the cloud, workspace-scoped host routes locally) — never via per-agent copies, never by waking pods to render a list. What the pi runtime reads is a **local mirror** of the store: pods hydrate the shared prefix beside their agent prefix (pod-store shared routes; the sync engine is this repo's `packages/runtime-client/src/object-sync/`), the resource loader gets a second skill path, and the workspace clamp (`WorkspaceGuard`) treats the shared dir as an extra writable root — agents read AND edit shared skills there, and pod-local edits push back to the store (see below).

The mirror is forced by pi itself, not chosen: pi 0.82.1 skills are path-based (`Skill` has no content field) and skill content is re-read **from disk at invocation time** — the model reads the `<location>` path via the `read` tool, and `/skill:name` does a raw `readFileSync`. In-memory/string skills do not exist (verified against `@earendil-works/pi-coding-agent` 0.82.1 source and bundled docs). So "single source of truth" means: duplication demoted from *truth* (visible, drifting, per-agent files) to *cache* (invisible, self-healing, hydrated). One edit in the store updates every agent.

Three semantics complete the design:

- **Assignment stays explicit** (HOU-792's UX): a skill existing in the store enables nothing. Each agent's `<agent>/.houston/skills-manifest.json` (`{ "enabled": [slugs] }`) says which shared skills load; the loader filters the shared dir by it (pi's `skillsOverride` hook) and unions with agent-local skills. "Install to N agents" = N one-line manifest writes. A bulk "enable for all agents" action is offered, but it is still N explicit manifest writes.
- **Agent edits ARE edits of the original** (decision revised 2026-07-30): the shared dir is a WRITABLE root for agent file tools — an agent editing a shared skill edits the one org copy, and every agent gets the new version. There is deliberately no fork-on-edit: individual users think of a skill as ONE thing, and a silent per-agent copy would betray that. On desktop the write lands directly in `<Workspace>/.shared/skills/`; on pods the mirror pushes skill writes back through the pod-store (`PUT` on the shared routes, last-writer-wins, local-wins on concurrent-edit conflicts, deletions never propagate — a locally deleted file self-heals from the store). **Deletion of a shared skill stays a human act through the UI.** Agent-local copies still shadow a same-slug shared skill as a deterministic collision rule, but the only flow that creates them is "Share to workspace" finding pre-existing divergent copies — never an edit.
- **Admin-only writes** (Teams/C7): owner/admin create/edit/delete org skills; members read and manage manifests for agents they can access. The gateway enforces; the client surface rides `/v1/capabilities`; desktop single-player is ungated.

Freshness: hydrate-on-wake covers asleep pods; awake pods check the org `.rev` before each turn (debounced; there is no gateway→pod push primitive, and none is needed — an asleep agent cannot be using a stale skill, and pi re-reads content from disk at every invocation). Pod-local skill edits push up promptly via a watcher on the mirror. **No migration** (decision revised 2026-07-30): prod agents own their skills individually and nothing pre-exists to migrate; the store starts EMPTY and a skill becomes shared only through the explicit "Share to workspace" act (promote: verbatim SKILL.md to the store, holders enrolled via manifests, only byte-identical copies removed).

Delivery: HOU-1027 (umbrella), HOU-1028–1031 (this repo: domain, runtime, host, frontend — fully functional offline on desktop), HOU-1032–1034 (cloud: pod-store shared routes, gateway CRUD, freshness; HOU-1035's migration job was canceled with the no-migration decision). Phase 2 couples an engine-image roll to a gateway roll — engine first, then gateway.

## Considered Options

- **Shadow-don't-mutate for agent edits** (the original design here): the mirror read-only to agents, an agent edit forking a per-agent override copy. Safer against a prompt-injected agent rewriting an org-wide skill, but rejected on product grounds (2026-07-30): users experience a skill as ONE thing, and fork-on-edit means "I told my agent to improve the skill" silently stops matching what every other agent runs. Retained backstops: agents cannot DELETE a shared skill, pod writes are restricted to the `skills/` sub-prefix, and every edit is visible to the whole workspace immediately.

- **Keep copies as truth, add drift metadata** (org-level source record + content hash so the UI can show/repair drift): cheapest step, but repair stays manual and "one edit updates everyone" never materializes. Rejected by decision (2026-07-29): go straight to the store.
- **In-memory skill injection** (pi `skillsOverride` with virtual content, or an upstream `content?: string` patch): metadata injects fine, but both invocation paths read `filePath` from the real filesystem, and Houston's clamp blocks out-of-workspace paths; an upstream patch breaks skills' sibling-file model (`scripts/`, `references/` relative to `baseDir`) and puts us on a fork. Rejected. (Contrast: org **context** CAN be string-injected — `agentsFilesOverride` takes `{path, content}` — which is why context riding these rails later is *easier* than skills.)
- **Materialize store skills into each agent's `.agents/skills/`** (store authoritative, existing dir as cache): avoids the clamp change, but shared and agent-owned files become indistinguishable on disk, and the agent's own skill dir doubling as a cache makes 'Share to workspace' and sync-back ambiguous. The dedicated mirror keeps the layers physically separate.
- **Dedicated org bucket**: prefixes already isolate; per-org buckets add IAM/lifecycle/hydration complexity for zero functional gain. Rejected.
- **Visible (non-dot) desktop folder** for discoverability: rejected — agent discovery treats non-dot workspace subdirs as agents (`store/local.ts` `listDirs` filters dot names), so `.shared/` is collision-free by construction, and discoverability is an in-app property (the Skills page searches shared + per-agent skills together; the product voice never points users at the filesystem).

## Consequences

- The Skills page's per-agent query fan-out (`use-workspace-skills.ts`) and copy-plan semantics (`planSkillAssignment` unify-on-save) are replaced by one store query + manifest writes; the pod-waking discipline problem for the UI disappears.
- Skills stop being purely agent-scoped for the first time: `packages/domain` gains workspace-scoped layout keys, and `WorkspacePaths` gains a workspace-level root beside `agentRoot`.
- The same rails (shared prefix + manifest + synced mirror + gateway CRUD) are the intended path for org context (easier: string-injectable) and, eventually, learnings — which stay a **non-goal** here because they are agent-written from many pods concurrently and need their own write-coordination design.
- Group shared context (sidebar `editContext`, copy/injection-based) is superseded in principle by the org layer, but is not touched in v1.
