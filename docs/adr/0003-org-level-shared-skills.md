# Org storage is the source of truth for shared skills

A skill shared across agents lives ONCE, at the org/workspace level: `ws/<org>/shared/skills/<slug>/…` in the cloud bucket (under the existing `OrgRoot` seam, beside agent prefixes) and `~/.houston/workspaces/<Workspace>/.shared/skills/<slug>/…` on desktop. Clients read and write that source directly (gateway routes `/v1/orgs/:org/skills…` in the cloud, workspace-scoped host routes locally) — never via per-agent copies, never by waking pods to render a list. What the pi runtime reads is a **read-only local mirror** of the store: pods hydrate the shared prefix beside their agent prefix (through new read-only pod-store routes; the sync engine is this repo's `packages/runtime-client/src/object-sync/`), the resource loader gets a second skill path, and the workspace clamp (`WorkspaceGuard`) grows read-only extra roots so the model can `read` shared SKILL.md files but `edit`/`write` still refuse them.

The mirror is forced by pi itself, not chosen: pi 0.82.1 skills are path-based (`Skill` has no content field) and skill content is re-read **from disk at invocation time** — the model reads the `<location>` path via the `read` tool, and `/skill:name` does a raw `readFileSync`. In-memory/string skills do not exist (verified against `@earendil-works/pi-coding-agent` 0.82.1 source and bundled docs). So "single source of truth" means: duplication demoted from *truth* (visible, drifting, per-agent files) to *cache* (invisible, self-healing, hydrated). One edit in the store updates every agent.

Three semantics complete the design:

- **Assignment stays explicit** (HOU-792's UX): a skill existing in the store enables nothing. Each agent's `<agent>/.houston/skills-manifest.json` (`{ "enabled": [slugs] }`) says which shared skills load; the loader filters the shared dir by it (pi's `skillsOverride` hook) and unions with agent-local skills. "Install to N agents" = N one-line manifest writes. A bulk "enable for all agents" action is offered, but it is still N explicit manifest writes.
- **Agent self-edits shadow, never mutate**: the shared mirror is read-only to the agent; an agent (or user) editing a shared skill for one agent produces an agent-local copy in `.agents/skills/<slug>/`, which **wins name collisions** against the shared skill. Divergence is thereby explicit, visible ("modified from org version"), and reversible (delete the override → back on the store version). Editing the store itself is a deliberate act through the UI, gateway-authorized.
- **Admin-only writes** (Teams/C7): owner/admin create/edit/delete org skills; members read and manage manifests for agents they can access. The gateway enforces; the client surface rides `/v1/capabilities`; desktop single-player is ungated.

Freshness: hydrate-on-wake covers asleep pods; awake pods check the org `shared_rev` at turn-start (there is no gateway→pod push primitive, and none is needed for v1 — pi re-reads content from disk at every invocation, so only name/description changes require a loader reload). Migration: byte-identical per-agent copies collapse into the store + manifest entries; divergent copies become agent-local overrides — never silently unified. Desktop migration is an idempotent boot migration in `packages/host/src/migrate/`; cloud is a gateway-driven idempotent job. The copy-based world is a valid degenerate state (empty store, everything an override), so the migration is rollback-safe.

Delivery: HOU-1027 (umbrella), HOU-1028–1031 (this repo: domain, runtime, host, frontend — fully functional offline on desktop), HOU-1032–1035 (cloud: pod-store shared routes, gateway CRUD, freshness, migration). Phase 2 couples an engine-image roll to a gateway roll — plan it like the gateway-catalog/engine coupling.

## Considered Options

- **Keep copies as truth, add drift metadata** (org-level source record + content hash so the UI can show/repair drift): cheapest step, but repair stays manual and "one edit updates everyone" never materializes. Rejected by decision (2026-07-29): go straight to the store.
- **In-memory skill injection** (pi `skillsOverride` with virtual content, or an upstream `content?: string` patch): metadata injects fine, but both invocation paths read `filePath` from the real filesystem, and Houston's clamp blocks out-of-workspace paths; an upstream patch breaks skills' sibling-file model (`scripts/`, `references/` relative to `baseDir`) and puts us on a fork. Rejected. (Contrast: org **context** CAN be string-injected — `agentsFilesOverride` takes `{path, content}` — which is why context riding these rails later is *easier* than skills.)
- **Materialize store skills into each agent's `.agents/skills/`** (store authoritative, existing dir as cache): avoids the clamp change, but the agent can silently edit the "cache", recreating drift, and cache-vs-override become indistinguishable on disk. The read-only mirror keeps the layers physically separate.
- **Dedicated org bucket**: prefixes already isolate; per-org buckets add IAM/lifecycle/hydration complexity for zero functional gain. Rejected.
- **Visible (non-dot) desktop folder** for discoverability: rejected — agent discovery treats non-dot workspace subdirs as agents (`store/local.ts` `listDirs` filters dot names), so `.shared/` is collision-free by construction, and discoverability is an in-app property (the Skills page searches shared + per-agent skills together; the product voice never points users at the filesystem).

## Consequences

- The Skills page's per-agent query fan-out (`use-workspace-skills.ts`) and copy-plan semantics (`planSkillAssignment` unify-on-save) are replaced by one store query + manifest writes; the pod-waking discipline problem for the UI disappears.
- Skills stop being purely agent-scoped for the first time: `packages/domain` gains workspace-scoped layout keys, and `WorkspacePaths` gains a workspace-level root beside `agentRoot`.
- The same rails (shared prefix + manifest + read-only mirror + gateway CRUD) are the intended path for org context (easier: string-injectable) and, eventually, learnings — which stay a **non-goal** here because they are agent-written from many pods concurrently and need their own write-coordination design.
- Group shared context (sidebar `editContext`, copy/injection-based) is superseded in principle by the org layer, but is not touched in v1.
