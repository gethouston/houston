# Protocol v3: the shared contract between host, runtime and clients

`@houston/protocol` (`packages/protocol/src`) is the one wire contract for every deployment (`PROTOCOL_VERSION` in `core.ts`). The frontend talks only to the host; the host talks to runtimes. The conversation core (`conversation.ts`) is the runtime's surface verbatim, nested under `/v1/agents/:id/conversations/*`, and `@houston/runtime-client` re-exports it. The package is a dependency-free leaf, which is why rules that two processes must agree on byte for byte live here rather than in either process.

## Changes are additive

Every field added since v3 is optional and its absence means the older behaviour, so older engines, gateways and stored files stay valid. Untrusted values are normalized by one parser per concept, shared by every hop that reads them, so the send route, the cloud turn parser and the host's forwarding hop never disagree:

- `normalizeTurnMode` and `parseTurnModePin` (`conversation.ts`): only the exact literals `execute`, `plan`, `auto` pass; anything else is the default, never a surprise mode. A pin of `null` or the empty string (what Go `omitempty` drops) is no pin, so the conversation's stored mode applies.
- `parseMentions`: non-arrays are nothing, entries need a non-empty string `userId`, the first entry per id wins so repeats cannot spend the budget, ids and names are clipped (128 and 256) rather than dropped because the id is what matters, at most `MENTIONS_MAX` (32) survive, and the scan stops after `MENTIONS_SCAN_MAX` (1000) entries. A bad sidecar never costs the person their message. An empty result is `undefined`, never `[]`.
- `parseTurnLimits` and `parseRoutineFloorHeader` (`turn-limits.ts`): a garbled stamp is no limit, never a stricter one and never a failed send. A floor above a day (`MAX_ROUTINE_MIN_INTERVAL_MINUTES`) would refuse every schedule, so it is not a floor. Node joins a repeated custom header into one string, which fails the digits check and reads as no floor.
- `parseMissionTitle` (`mission-title.ts`): malformed means no title, never a refused turn.
- `parseModelCallReport` (`model-call-report.ts`): a malformed top level is no report, a malformed entry drops alone, and calls past `MODEL_CALL_REPORT_MAX_CALLS` (64) are counted in `droppedCalls`. The report feeds gateway latency metrics and is never shown to a person.
- `parseMessageApprovals` (`domain/approval.ts`) is fail-closed: anything not a well-formed receipt is dropped, so an unreadable field approves nothing and the person is asked again.

## The conversation stream

`WireFrame` (`wire.ts`) is a `WireEvent` plus a per-conversation `seq`, strictly increasing from 1 and assigned by the stream's one fan-out authority (the runtime's bus, or the host's turn relay for cloud conversations). The authority stamps every frame itself and never passes an upstream seq through. The counter lives for the authority's process and is not reset when the replay buffer clears at turn end.

- **Resume.** Each frame carries an SSE `id`. A client reconnects with `?after=<seq>` or `Last-Event-ID`; the header wins, because the gateway advances it past its own replay while the query parameter rides along unchanged. Frames still in the replay window are re-sent in order without a `sync`. A cursor that cannot be served gets a fresh `sync` with `resync: true`, and the client must refetch instead of splicing.
- **Turn identity.** The turn's server mints a `turnId` and stamps it on every turn-scoped frame, including terminal frames the relay synthesizes for a dead turn, and persists it on the turn's user and assistant messages. A `sync` carries the running turn's id in `data.turnId`. This is what lets a client tell another writer's turn (a teammate, a second tab, a routine) from its own.
- **`provider_error` ends the turn.** The server deliberately skips the clean `done` after one, because a `done` would settle the chat as a success. Consumers must treat it as terminal.
- **`reply_complete`** is emitted at most once and never after a terminal frame. It is not terminal; the client may hand the card back early but keeps the turn live. `OFFER_TOOL_NAMES` and `isOfferToolName` (`reply-complete.ts`) name the offer tools that do not count as the turn carrying on, stripping the Claude SDK's `mcp__<server>__` prefix first.
- **`done` never picks the board status.** `pendingInteraction` on it describes what the settled card shows; a clean finish always settles `needs_you`. Only the person closes a mission.
- A running `sync` carries `thinking` and `tools` so a client attaching mid-turn replays what streamed before it connected. In `tools`, `isError` present means the tool ended.
- `TOOL_RESULT_PREVIEW_MAX` (4,000) is applied at the emitting backend, so everything downstream already holds clipped text.
- `user.mentions` rides the frame only to mirror what was stored. Nothing reads it today; live clients chip from the history reseed.

## Persisted messages carry what a reload needs

`ChatMessage` (`conversation.ts`) persists everything a client that missed the live stream needs to render the same transcript: `turnId`, tool `input` and `result`, `thinking`, `usage`, `providerSwitch`, `compaction`, `contextCleared`, `fileChanges`, `providerError`, `pendingInteraction` (only on a clean end, the same condition that attaches it to `done`), `stopped`, and `interrupted`.

- `displayText` is presentation only; the model always ran on `content`, and a replay renders `displayText ?? content`.
- `contextCleared` marks a `/clear`. The transcript replay that rebuilds a backend session starts after the newest marker, which keeps pre-clear messages out of the model's context while they stay visible and searchable.
- `compactionSummary` marks a summary the chat never shows. `isCompactionSummary` (`compaction-summary.ts`) also recognizes older summaries by shape, because cloud conversations hold them and no boot migration reaches them. A turn's last record is never a summary, so a stopped cloud turn's partial reply stored with `compaction` and no usage still shows.
- `interrupted` is written at boot by the engine for a turn its previous process died in, since nothing could stamp it at the time. `resumed` means the engine is already running a replacement turn, which keeps it out of the error and `needs_you` settles. `TurnInterruptionCause` is a discriminated field so the next cause is a value, not another flag.
- `offset` and `totalMessages` on a history read: absent on pre-windowing servers, read as 0 and `messages.length`.
- `ConversationImportRequestSchema` (`conversation-import.ts`) writes lines said elsewhere as history with no turn. Every message carries the import's turn id, so a retry of a landed import writes nothing, and each imported entry gets its own turn id so no two read as one turn.

## Providers and their failures

- `ProviderId` (`conversation.ts`) names the connectable providers and widens with `string & {}`, because pi's catalog (about 35 providers) drifts. `openai-compatible` is local profile only: its URL is the person's own machine, unreachable from the cloud. `INTEGRATION_PROVIDER_IDS` (`integration-provider.ts`) is the opposite, a closed set, because an integration provider is a Houston adapter that exists only if this repo ships one (`composio`, `custom`).
- `ProviderHealth` is richer than `configured`: a credential can be valid and out of credits, or present and dead. `credentialScope` is omitted unless the request carried an acting identity, so desktop, self-host and routines see the shape they always saw. `reconnectBy` is set only by the hosted gateway on a Claude subscription login, which ends about 28 days after sign-in however often it is refreshed.
- `ProviderError` (`provider-error.ts`) mirrors the frontend card union. `usage_limit_paused` (a subscription window used up: wait for `resets_at` or switch model) is distinct from `rate_limited` (seconds) and `quota_exhausted` (pay or switch; opencode.ai sends it as `401 CreditsError`, so it must not render a reconnect card). The routine scheduler snoozes on `usage_limit_paused`. `context_overflow` carries the provider's real window, which also corrects an over-assumed custom endpoint window. `undelivered_prompt` is set when pi raised a missing credential before recording the message, so the reconnect retry must re-deliver it; it differs from the client-only `failed_prompt`.
- `AuthFailureCause` (`provider-error-parts.ts`): `org_policy_blocked` and `billing_locked` are not healed by reconnecting. `billing_locked` is minted only by the SDK from the gateway's `provider_account_blocked` send refusal, and `PROVIDER_ACCOUNT_BLOCKED_CODE` is the one string the host, the runtime's serve probe and the SDK read. Azure's `DeploymentNotFound` is its own `ModelUnavailableReason`, because the card must say to deploy the model, not pick another. `ProviderErrorCredential` names whose account hit the wall in a team space, where every turn runs on the acting member's own account; it only names and never unlocks an action.
- `ClaudeOAuthCredential` (`claude-oauth.ts`) is the Claude CLI's `.credentials.json` verbatim, carried unchanged from desktop to host to pod to disk so no re-encoding can corrupt what the SDK reads. `parseClaudeOAuthEnvelope` requires only a non-empty `accessToken`: rejecting a real credential over a field Houston does not interpret would send every person to the paste fallback. Present fields are type-checked, absent ones stay absent so the file stays byte-faithful, and no extra keys pass through.
- `deadGoogleApiKey` (`google-key.ts`) is a denylist of shapes that can never be a Google API key (an OAuth access token `ya29.…`, a JWT `eyJ…`). It used to allowlist `AIza`, then AI Studio shipped `AQ.` keys and the allowlist refused every one and reported the stored row for deletion. Every new paste is live-verified (`packages/runtime/src/auth/verify-api-key.ts`), so an unknown future format must fail open here.
- `provider-catalog.ts` is pi's baked registry, identical on desktop and in an egress-locked pod, so it needs no runtime schema. `runsAs` on a retired row admits the model it runs as, on that provider only, for both the gateway's clamp and the app. `pin` carries what the host's `start_mission` pin resolution reads (`routes/missions-provider.ts`), so the gateway resolves pins from these values rather than a copy of the host's tables.

## Context windows

`model-windows.ts` is the one source for window sizing, shared by the app's context bar and the runtime's autocompact and provider-switch decisions. They used to size windows separately: the runtime never compacted a 200k-real Claude chat that pi reported as 1M, and needlessly compacted Gemini chats pi under-reported.

- `MODEL_WINDOW_OVERRIDES` lists only models whose real window differs from pi's raw value, keyed by pi provider id (`openai-codex`, not the app's renamed `openai`). Codex rows sit at 95% of pi's window, because Codex's `/status` reports a 95%-effective window (272,000 × 0.95 = 258,400), and each row carries the ceiling of Codex's opt-in larger window (872,000 × 0.95 = 828,400, read from the Codex models listing on 2026-11-17). Anthropic has no row: its current lineup runs a native 1M window on every plan. Every row names a model `VALID_MODELS` in `@houston/domain` still lists, because a stale ceiling is worse than none.
- `effectiveModelWindow` starts at the default and snaps up to the ceiling once observed usage exceeds the default, since the provider compacts before its limit and usage can never exceed the true window. It is floored at observed usage so a wrong ceiling never reads over 100%.
- `autocompactPoint`: compact at 93% (`AUTOCOMPACT_THRESHOLD_PERCENT`), capped at `AUTOCOMPACT_CEILING_TOKENS` (200,000) for windows under `LONG_CONTEXT_WINDOW_TOKENS` (1M), because every request re-sends the whole context and a large window left to fill costs input tokens on every call. A 1M window skips the ceiling, so long chats keep their history word for word; 93% (930k) also keeps Houston's between-turn compaction ahead of the Claude CLI's own at 967k. Never past 93% of the model's input cap: GPT-6 and GPT-5.6 accept only `GPT_6_MAX_INPUT_TOKENS` (922,000) of their 1,050,000 window, and `GPT_6_LINE` matches every gateway spelling of those ids.
- `compactionWindow` is what the bar divides by, so 93% on the bar is where the runtime compacts for every model.

## Interactions and approvals

A pending interaction (`domain/interaction-types.ts`) is the ordered steps a turn ended on: up to three questions, then at most one sign-in, then connect steps (plus credential and hands-on steps). `suggest_actions` and `suggest_reusable` are non-blocking offers that render above the composer and outlive a move to done.

- `parsePendingInteraction` (`domain/interaction.ts`) drops unknown or malformed steps instead of failing, because interactions outlive code and a mixed-version peer may carry a kind this build dropped. Pre-step shapes from older builds parse to nothing. Read seams use the parse so dropped steps never reach a renderer.
- `resolveInteractionPatch` is the one rule every activity write seam applies (the host's `applyActivityUpdate`, the app's `applyActivityPatch`, the fake host): `null` clears, a valid object replaces and is stored verbatim so a newer peer's step kind survives, and absent or malformed leaves it alone. Malformed counts as absent on purpose: a `status: "done"` patch with a junk interaction must still strip the blocking steps and keep only the offers (`retainSuggestionSteps`), or a Done card would show a question stepper.
- `hasOnlySuggestionSteps` is the one spelling of "offers only"; an empty sequence is not.
- `HANDS_ON_SURFACES` is closed: the app navigates by it, so `request_hands_on` refuses an unknown screen at the source and an unknown one renders as unavailable. Growing it means teaching the app the screen in the same change. A hands-on step for one employee's screen needs `agentId`; a surface never guesses it.
- **Approvals** (`domain/approval.ts`): a model cannot create an approval. The host issues a `requestId` when it raises the card, and only a user message carrying it turns it into a receipt. Assistant messages never travel the user-message route, and a routine's unattended turn is fired straight at the runtime. The receipt rides its own `approvals` field, never inside the text, because the text is the person's words and a hidden marker can be stripped wrongly. The host records receipts and drops the field before forwarding. A step's `approval` block is trustworthy only with a host-issued `requestId`; a step whose id the host did not issue has it stripped, and a surface must then ignore the block. `ApprovalArg` is structural so the surface can show the exact call in the reader's language, since a person cannot approve what they cannot read; a value past the host's limit is cut with `truncated` set, never abbreviated silently.
- `ROUTINE_FIRE_HEADER` (`routine-fire.ts`) marks a routine run's message. The host sets it only in `fireTurn` and forwards client requests with a header list it builds itself, so a client cannot add it. The runtime lets a marked message answer a card left by another run, because a routine's runs share one conversation and act as different people.

## Activities, routines and other domain shapes

- Activity fields are snake_case because the wire mirrors the on-disk `.houston` schemas (`domain/activity.ts`). `claude_session_id` is a legacy name baked into user data and stays.
- Server-stamped fields are never accepted from a create body or PATCH: `started_by`, `origin_session_key`, `origin_agent`, `origin_depth`, `contributors`, `mentioned`, `created_by`. A raw file write or import carries whatever the file holds. `origin_agent` is also an authorization input: an agent may move a mission on another board only when it matches its own, stamped in cloud from the gateway-verified `x-houston-calling-agent` header. `origin_depth` bounds delegation chains across pods. Identity fields are absent on desktop so those files stay byte-identical.
- `skill_slug` is the durable half of the skill-to-chat link, because agents rewrite `SKILL.md` but never `activity.json`. A send's mode pin never rewrites `Activity.mode`; only picking the conversation's mode does. An empty or whitespace title is refused, because a card shows nothing else.
- Routines (`domain/routine.ts`) have exactly one of `schedule` or `trigger`. A trigger binding with no `kind` is Composio, so routines written before webhook wakes read unchanged; a webhook binding requires `kind`. Webhook URLs and secrets never live in routine data. `auto_paused` and `snoozed` are server-owned and never written by an update. `RoutineSnooze` leaves `enabled` true and expires by the clock, because a podless cloud agent has no writer to clear it.
- `RoutineAutoPause.cause` exists because clients older than the field crash on an unknown `reason`, and the gateway serves the file to every client version. So a `no_model` pause is written as `reason: "model_unavailable"` with an empty `provider`, and newer clients read `cause` first (`domain/routine-failure.ts`). Delivery failures (`RoutineDeliveryFailureCode`) never feed the auto-pause streak.
- `DEFAULT_HEARTBEAT_SETTINGS` (`domain/heartbeat.ts`): features default on, so an absent document is a briefing at 08:00.
- `parseSidebarLayout` is the strict check both the host route and the gateway apply. Names count code points (the gateway counts runes) and ids, icons and colors count UTF-8 bytes (the gateway's `len`), so the two enforce identical limits (`domain/sidebar-layout.ts`). `normalizeSidebarLayout` coerces untrusted copies into an accepted layout, keeping anything that still identifies a group.
- `Workspace.folderPath` is opaque everywhere: a real path on the local profile, a synthetic key in cloud.
- `firstDay` in `domain/config.ts` is host-owned; config writes preserve it, and a first day is never born started.
- `HoustonEvent` (`events.ts`) keeps the Rust engine's event vocabulary so the app's event-to-query-key map survived the convergence. Detection differs by profile (file watcher locally, post-turn sync diff in cloud); the vocabulary does not.

## Codes both ends must share

Several codes live here because a status alone cannot identify a state: once a route grows a second 409, a client keyed on status explains the new state with the old copy and silences its report.

- `FileOpCode` (`domain/file-refusal.ts`): includes `NAME_TAKEN` (shared with agent create, install and rename), `NAME_RESERVED` (the AI Manager's name, compared as `agentNameKey`; an employee that already holds it keeps it) and `READ_ONLY` (storage refusing every write while reads work).
- `plan-min-interval.ts`: the `400 plan_min_interval` body and its one parser, minted by the host's routine write gates and read by the client.
- `routine-refusal.ts`: `routine_not_found`, also read by the runtime's op worker to heal its mirror. Older gateways answer only `ROUTINE_NOT_FOUND_REASON`, matched exactly so no other 404 reads as this one.
- `preference-create.ts`: create-only preference writes use a body field `onlyIfAbsent` and answer `412 preference_exists` with the stored value. It is a body field, not `If-None-Match`, because the gateway's CORS allow-list does not carry that header.
- `turn-error.ts`: unknown codes stay errors; older gateways omit the code.

## Byte-level agreements between processes

- `ATOMIC_TMP_SUFFIX` (`scratch.ts`) is `.houston.tmp`, the one name for a half-written file. Durable writes go to a temp file in the destination's directory and rename, so the temp lands inside the tree the store sync walks and the Files tab lists, and both must skip it. A plain `.tmp` once excluded a person's own `notes.tmp` at pod teardown. Pass `unique` to `atomicTempPath` wherever two writers can target one destination.
- `AUTO_CONTINUE_MARKER` and `HEARTBEAT_MARKER` (`auto-continue.ts`) tag messages Houston sends on the person's behalf. The model ignores the leading HTML comment and every transcript hides the bubble. The app and the runtime's restart resume both mint the first, and the host and gateway both mint the second, so a drift would show the person a prompt they never wrote.
- `accessDigest` (`access-digest.ts`) names a rejected token by lowercase hex sha256, so a revocation report can drop exactly that token without carrying it across processes or into logs. It must match the gateway's `store.AccessDigest`, and the match is case-insensitive so an upper-cased digest is not treated as some other token.
- `messageAdmissionFileName` (`message-admission-file.ts`) is where a message's admission receipt lives. The runtime writes it before executing and the host reads it before touching approvals; if they disagree by a byte, every retry reads as a new message and runs twice.
- `access-digest` and `message-admission-file` use `node:crypto`, so they are subpath exports only and stay out of the browser-facing barrel. Other subpaths (`auto-continue`, `google-key`, `model-windows`, `approval`, `file-refusal`, `plan-min-interval`, `routine-refusal`, `interaction`, `interaction-types`) exist for the app's `node:test` runner; they use erasable syntax and avoid runtime relative imports, which Node cannot resolve without extensions. That is why `domain/interaction.ts` imports types only, and why the closed hands-on vocabulary is re-exported from `index.ts` straight from the type module.

## Capabilities

`Capabilities` (`core.ts`) describe the deployment. The UI gates affordances on them, never on whether it is web, desktop or cloud, because that is where drift starts. `profile` is for diagnostics only. Absent flags mean a host that predates them.
