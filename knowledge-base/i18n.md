# Internationalization (frontend)

Houston ships in **en**, **es**, **pt**. On the web/desktop frontend every user-facing string flows through i18next. No literal English in JSX, props, placeholders, aria-labels, toast titles, or error messages. The native iOS app ships the same three languages on Apple's String Catalog instead — its own section at the end of this doc.

## Stack
- `react-i18next` + `i18next` + `i18next-browser-languagedetector`
- Config: [app/src/lib/i18n.ts](../app/src/lib/i18n.ts) — singleton, initialized synchronously at module load
- Resources: `app/src/locales/{en,es,pt}/<namespace>.json` — 23 namespaces per locale; `check-locales` is the authority. Newest: `auth` (the full sign-in screen: title, provider buttons via `continueWith` interpolation, email-code entry under `email.*`, last-sign-in hint).
- Type augmentation: [app/src/types/react-i18next.d.ts](../app/src/types/react-i18next.d.ts) — `t()` keys are compile-time checked

## Namespaces (23)
`common` (default), `aiHub`, `auth`, `setup`, `legal`, `shell`, `dashboard`, `settings`, `chat`, `board`, `agents`, `skills`, `routines`, `providers`, `errors`, `events`, `integrations`, `migration`, `portable`, `store`, `context`, `teams`, `agentOnboarding`.

Two namespace keys are camelCase over a kebab-case file: `aiHub` = `ai-hub.json`, `agentOnboarding` = `agent-onboarding.json`. Pick the namespace that fits; don't dump everything in `common`. `teams` holds all multiplayer/org copy (org dashboard, roles, Share dialog, managed-agent notices, templates, allowlists) — see `knowledge-base/teams.md`.

Add a namespace: create `en/<name>.json`, `es/<name>.json`, `pt/<name>.json`, register in `i18n.ts` (import + resources object + ns array), augment in `react-i18next.d.ts`.

## Patterns

**1. Plain string**
```tsx
const { t } = useTranslation("settings");
<h1>{t("title")}</h1>
```
JSON: `{ "title": "Settings" }`

**2. Variable interpolation** — never concatenate fragments (word order differs across languages)
```tsx
<p>{t("switched", { provider })}</p>
toast({ title: t("deleteTitle", { name }) })
```
JSON: `{ "switched": "Switched to {{provider}}" }`

**3. Pluralization** — i18next picks the right key by `count`
```tsx
<span>{t("appCount", { count })}</span>
```
JSON: `{ "appCount_one": "1 app", "appCount_other": "{{count}} apps" }`

**4. Embedded markup** (bold, links) — use `<Trans>` with named components, never split
```tsx
<Trans i18nKey="setup:provider.description"
  components={{ emph: <strong className="..." /> }} />
```
JSON: `"description": "Houston uses <emph>your own</emph> subscription."`

## Library boundary (ui/)

`ui/@houston-ai/*` packages stay i18n-agnostic. They take **optional `labels?` props with English defaults**. The app passes `t()` results in.

```tsx
// ui/skills/src/skill-marketplace-section-labels.ts
export interface SkillMarketplaceSectionLabels extends SkillMarketplaceGridLabels {
  heading?: string
  subheading?: string
  // ...
}
export const DEFAULT_SKILL_MARKETPLACE_SECTION_LABELS:
  Required<SkillMarketplaceSectionLabels> = {
  heading: "Discover skills",
  subheading: "Add ready-made skills from the community",
  // ...
}

// app/src/components/agent/use-skill-surface-labels.ts — ONE hook fills the bundle from t()
export function useSkillMarketplaceSectionLabels(): SkillMarketplaceSectionLabels {
  const { t } = useTranslation("skills")
  return { heading: t("store.heading"), subheading: t("store.subheading"), /* ... */ }
}

// app/src/components/agent/skill-discovery-tabs.tsx — the consumer passes it in
<SkillMarketplaceSection labels={{ ...marketplaceLabels, heading: undefined }} />
```

Label types COMPOSE rather than flatten (`SkillMarketplaceSectionLabels extends
SkillMarketplaceGridLabels`, which nests its own card + preview label types), so a
sub-component's copy is filled once and the consumer overrides one field where a surface
differs — above, the page header already names the area, so the section drops its heading.

Existing consumers without `labels` keep the English defaults — zero-break refactor.

For deep prop cascades (e.g. `AIBoard > KanbanColumn > KanbanCard`) thread the labels object through each layer (`cardLabels` etc.) and re-export the type from the package's `index.ts`.

## Multi-namespace components
```tsx
const { t } = useTranslation(["skills", "common"]);
t("skills:detail.delete")
t("common:actions.cancel")
```
First entry is the default namespace. Always prefix when in doubt.

## Navigation labels (there is no agent tab strip)
The per-agent tab shell is gone, and with it the `agents:tabLabels.*` and `shell:tabActions.*` blocks and the id-keyed `t(\`agents:tabLabels.${tab.id}\`, { defaultValue: tab.label })` idiom. The namespaces themselves are unchanged. Navigation copy now lives in two places, both plain static keys wired in `app/src/components/shell/sidebar-chrome.tsx`:

- **`shell:sidebar.*`** — the top-level rail entries (`missionControl`, `integrations`, `skills`, `aiModels`, `agentStore`, `settings`) plus `sidebar.yourTeams` / `sidebar.newTeam` and the team menu family `sidebar.teams.*`.
- **`shell:sidebar.teamSections.*`** — a team's destination rows (`missionControl`, `routines`, `files`, `settings` = "Team Settings"), built by `buildTeamSectionLabels`.

The agent settings page's rail titles are NOT a third block: they reuse `agents:subTabs.*` (job description, Skills, Learnings) + `teams:agentAdmin.rows.*`, with `teams:agentSettings.groups.*` for the two group headings.

## First-party agent catalog (`agents:catalog.*`)

Houston's own agents carry translated display copy under `agents:catalog.<id>.{name,description}`. Ten ids ship: `personal-assistant`, `blank`, plus the eight bundled store agents (`bookkeeping`, `legal`, `marketing`, `operations`, `people`, `sales`, `support`, `outbound`).

- The gate is **`localizeCatalogCopy(entry, t)`** (`app/src/agents/catalog-labels.ts`): it localizes only when `entry.author === "Houston"`, so a third-party / community agent sharing a first-party id is never relabeled (author's language wins). Missing `catalog.<id>` keys fall back to the entry's own English via `defaultValue`.
- It takes the minimal `{ id, name, description, author }` shape, so an `AgentConfig` and a store listing both pass straight in.
- **One call site**: `app/src/components/shell/naming-step.tsx` — the create-agent dialog's naming step, for the header name of the agent being created. The in-dialog catalog GRID is gone (PRODUCT-1171): step 1 is `agent-picker-step.tsx`, two choice cards (open the Agent Store page / start from scratch, which is always the `blank` config). `experience-card.tsx` survives only as a re-export shim for the avatar helpers in `agent-avatar.tsx`.
- The catalog data is TS, not Rust and not fetched: `app/src/agents/builtin/store-catalog.ts` is GENERATED by `scripts/gen-agent-templates.mjs` from `store/agents/<id>/houston.json`, and `app/src/agents/builtin/index.ts` concatenates it after `personal-assistant` + `blank`.

**Adding a new first-party agent** = add its `catalog.<id>.{name,description}` block to en/es/pt `agents.json`. English mirrors the catalog copy (source of truth stays in `store/agents/<id>/houston.json` / the builtin config); es/pt are the real translations. `pnpm check-locales` enforces that all three locales carry the same `catalog.<id>` keys.


## Store skills are translated at the CONTENT level (not a locale-JSON catalog)

Skills packaged with the first-party store agents ship as **fully translated SKILL.md files**: a Spanish workspace seeds Spanish skills, the agent loads the Spanish procedure, and the user edits Spanish text (HOU-715). There is no per-skill locale-JSON catalog; the skill file itself is the single source in the user's language.

- **Translated sources**: `store/agents-i18n/<lang>/<id>/.agents/skills/<translated-slug>/SKILL.md` (en source stays `store/agents/<id>/...`). Slug/title/category mapping: `store/skills-i18n.json`.
- **Slugs are translated but ASCII** (`planear-una-campana`); the accents live in the new frontmatter **`title:`** field ("Planear una campaña"), surfaced as `SkillSummary.title` / `SkillDetail.title` and rendered via `skillDisplayTitle` (`app/src/lib/humanize-skill-name.ts`). Never put accents in a slug; never show a de-accented slug as a title.
- **Cross-references**: translated SKILL.md sources keep ENGLISH slug tokens verbatim (translators treat them as identifiers). `scripts/gen-agent-templates.mjs` is the single place tokens are renamed — it emits `store-templates/<id>.<lang>.json` payloads with the skills tree swapped, every slug token rewritten (bodies, CLAUDE.md, data-schema.md, manifest agentSeeds), plus a `skillRenames` map.
- **Locale variant lookup**: `loadStoreTemplate(id, lang)` (`app/src/agents/builtin/store-template-loader.ts`) reads `store-templates/<id>.<lang>.json`; its one consumer is the migration below.
- **Existing agents**: `useStoreSkillLocaleMigration` (mounted in `use-agent-chat-panel`) lazily swaps a skill whose content is byte-identical to the packaged English version for its translated file and token-rewrites the agent's CLAUDE.md/data-schema.md. Edited skills are never touched (author's language wins). See `app/src/lib/store-skill-locale-migration.ts`.
- **Drift guard**: `app/tests/store-skill-i18n.test.ts` pins the translated trees + generated payloads to the en store (missing translations, em dashes, non-kebab slugs, stale payloads all fail CI). Adding/renaming/re-describing a store skill = translate it in both langs, update `store/skills-i18n.json`, rerun the generator.
- **Do NOT key anything on `Agent.configId`** — the host never persists which template an agent was created from; the engine adapter's `toUiAgent` (`packages/web/src/engine-adapter/cp/agents.ts`) fabricates `configId: DEFAULT_AGENT_CONFIG_ID` (`"personal-assistant"`) for every agent. Identify store skills by content, as the migration does.
- Translated skills carry a translated `category:` for the skill preview modal; `localizeSkillCategory` (`skills:categories.<name>`, `app/src/lib/localize-skill-category.ts`) still localizes English-seeded category values where they appear.
- es titles are infinitive, verb-led, founder-voice ("Registrar un gasto", "Fechar meu mês"); Spanish LatAm tú, Portuguese BR você; no em dashes anywhere in skill files.

## Locale source of truth

Two **engine-owned** sources, resolved as: **active-workspace `locale` override → global `locale` preference → `navigator` → `en`**. The engine, never the browser, owns both — so a fresh browser pointed at a headless engine (the `houston webapp` against a container) shows the stored language instead of whatever happens to be in that browser's localStorage.

- **Global default** = engine preference `locale` (BCP-47 base tag `en`/`es`/`pt`), the value the first-run picker writes. Also the fallback for any workspace without an override.
- **Per-workspace override** = the `locale` field on the workspace record, set via **`PATCH /v1/workspaces/:id`** with `{ "locale": "pt" }` in the body (`packages/host/src/routes/account.ts`; owner-only, 403 otherwise, 503 without a vfs). The host stores it as the workspace's `locale` preference (`ws/<workspaceId>/preferences.json`) and echoes the updated workspace back. A workspace that never picked a language has no key (inherits the global default); `null` clears it.
- **Boot-apply (the part that was missing):** [`useLocalePreference`](../app/src/hooks/use-locale-preference.ts), consumed by [LanguageGate](../app/src/components/shell/language-gate.tsx), resolves the effective locale and calls `applyEngineLocale` so the engine value is actually *applied* to the live i18n instance — not just read. Re-applies when the active workspace changes. The gate holds its blank screen until the first apply lands (no flash of the wrong language).
- **First-run picker** ([LanguageGate](../app/src/components/shell/language-gate.tsx)) writes the **global default** (no workspace exists yet) before the disclaimer. Picking a language **advances immediately** (no Continue button). `setLocale` applies the i18n swap + boot cache FIRST (that local change is what the gate advances on) and persists the account preference **best-effort**: the gate runs before sign-in, so a hosted gateway can reject the write with no bearer yet — that failure is logged and the flow still advances (the choice re-syncs once authed), never a silent dead-end.
- **Settings → Workspace language picker** ([language.tsx](../app/src/components/settings/sections/language.tsx)) writes the **active workspace's** override (it lives under the Workspace settings tab).
- localStorage cache `houston.locale.cache` is **boot-time flash-avoidance only**, never the source of truth.
- Pure value-logic (`isSupported`, `normalizeLocale`, `resolveEffectiveLocale`, `localeToApply`) lives in [`app/src/lib/locale.ts`](../app/src/lib/locale.ts) — DOM/JSON-free so it unit-tests under bare Node (`app/tests/locale.test.ts`); `i18n.ts` re-exports it.
- Engine itself is locale-agnostic — surfaces both values verbatim.

## Updater release notes (en/es/pt)

The "update available" card shows the release notes in the user's language. Authoring is NOT a `t()` namespace — the notes are markdown written per release under `.github/release-notes/<version>.{md,es.md,pt.md}` (English base + optional translations). The Tauri updater only carries one notes string, so CI packs the translations into a trailing `<!--houston-i18n:{...}-->` comment; [`selectUpdateNotes`](../app/src/lib/update-details.ts) strips it and picks the translation for `i18n.language` (which already encodes the workspace-override → global resolution above), falling back to English. Full mechanism + authoring rules: `.github/release-notes/README.md` and `knowledge-base/production-infra.md` (Auto-updater). Same copy rules apply (no em dashes, Spanish neutral LatAm, Portuguese Brazilian).

## What does NOT translate
- Brand names: Houston, Claude, OpenAI, Anthropic, GitHub, Google, Gemini
- Code identifiers, file paths, CLI commands, env var names (e.g. `GEMINI_API_KEY`)
- **Third-party / community** agent store listings — author's language wins; treated like App Store listings. (Houston's own **first-party** agents ARE translated — see "First-party agent catalog" above.)
- Engine-side error strings (currently English; future work: error code → i18n key map)
- Console / log messages
- The WebView compatibility gate ([app/public/compat-gate.js](../app/public/compat-gate.js)) — it runs before the bundle (and thus before i18next) to catch engines too old to load the app, so its en/es/pt strings live inline and are picked by `navigator.language`. Keep them in sync with the product voice (no em dashes).

## Pre-commit checks
```bash
cd app
pnpm tsgo --noEmit      # types + i18n key validity
pnpm check-locales      # missing keys, shape drift, placeholder parity, em dashes
```
Both must pass. The locale validator catches structural drift between en/es/pt automatically.

## Wiring a new screen — checklist
1. Pick the namespace (or create one).
2. Add the keys to `en/<ns>.json`. Use nested objects, not flat `screen_section_label` keys.
3. Translate to `es` and `pt` in the same shapes (no empty stubs — fall back to en is for runtime resilience, not authoring).
4. `useTranslation("<ns>")` in the component (or `["<ns>", "common"]` for multi-ns).
5. Replace every literal string with `t(...)`.
6. If the component is in `ui/`, add a `labels?` prop instead and pass `t()` from the consumer.
7. Run `pnpm tsgo --noEmit && pnpm check-locales`.
8. Commit.

## Routines labels (dynamic schedule/time copy)

The `routines` namespace covers everything in a team's Routines section. `@houston-ai/routines`
is i18n-agnostic: every component takes `labels` props (English defaults in
`ui/routines/src/labels-default.ts`, types in `ui/routines/src/labels.ts`) plus a
BCP-47 `locale`. The app builds the whole bundle once with
[`useRoutineLabels`](../app/src/hooks/use-routine-labels.ts)
(`t("routines:<group>", { returnObjects: true })`) and threads its six fields —
`labels.grid`, `labels.rowLabels`, `labels.schedule` (whose `.summary` feeds the
row's cron summary), `labels.nextFire`, `labels.trigger`, and `labels.locale` —
into `RoutinesGrid`
(`components/team-view/team-routines/team-routines.tsx`), which fans them out to
the rows, the inline schedule-edit popover (`RoutineRowScheduleEdit`), and
`ScheduleBuilder`.

Two things make this group different from static namespaces:

- **`{token}` (single brace), not `{{token}}`.** Schedule summaries and relative
  times ("Runs every {n} minutes", "Next run {relative}") interpolate numbers and
  times that are computed inside `ui/`, not at the `t()` call site. We read the
  templates with `returnObjects` and pass no interpolation values, so i18next must
  leave the placeholders intact — double-brace tokens would be eaten. The package's
  `interp(template, vars)` (in `ui/routines/src/labels.ts`) fills the single-brace
  tokens. The locale validator only checks `{{ }}` parity, so single-brace tokens
  are invisible to it; **keep them identical across en/es/pt by hand**. (Deliberate
  exceptions: `schedule.summary.monthly` and `schedule.summary.everyNMonths` use
  `{ordinal}` in en and a plain `{n}` day in es/pt — `interp` is handed both, plus
  `{months}` for the every-N-months interval count.)
- **Day/month names, AM-PM, date order, and list joining all come from
  `Intl.*Format(locale)`**, never from per-language strings. That is why
  `useRoutineLabels` maps the app locale to a region (`pt` → `pt-BR`) and passes it
  down. The pure formatters live in `ui/routines/src/schedule-format.ts`:
  `formatTime` is locale-driven (12h en, 24h es/pt) and normalizes the U+202F narrow
  no-break space ICU puts before AM/PM back to a plain space; `weekdayName` /
  `shortWeekdayNames` give localized day names for the weekly summary + day-of-week
  picker. The custom weekly summary (`summary.weeklyOnDays`, the `{days}` token) joins
  its localized weekday list with `Intl.ListFormat(locale, { type: "conjunction" })`, so
  the connector localizes ("and" / "y" / "e") and en gains the Oxford comma.
- **Unit names are two flat sibling maps, not a plural pair.** `schedule.units` and
  `schedule.unitsSingular` each hold four plain strings over the SAME four keys,
  `minutes` / `hours` / `days` / `months` (there is no `weeks` unit), and the
  "Repeat every N …" picker reads whichever map the count calls for. Keep the two
  maps' key sets identical. The rest of the custom picker: `repeatEvery`,
  `enterNumber`, `decrease` / `increase`, `weekdaysLabel` ("On these days", the
  weekday multi-select), `weekdayShortcuts.{everyDay,weekdays,weekends}`,
  `dayOfMonthLabel`, `timeLabel`, `timePicker.{hour,minute,period}`, and `pickDay`
  (the "no day selected" validation summary). The fixed cron choices are
  `schedule.presets.{every_30min,hourly,daily,weekly,monthly,custom}`.

## iOS (native SwiftUI app) — a separate toolchain

Nothing above this heading applies to iOS: no i18next, no `locales/*.json`, no `check-locales`. The iOS app (`mobile/ios`) ships the same en/es/pt set on Apple's stack, and only the copy rules (glossary, tone, no em dashes) carry over.

- **Copy lives in `Strings*.swift` files** (one per surface, extensions on the `Strings`
  enum). Every member resolves through `String(localized: "<key>", defaultValue: "<en>")`;
  the en `defaultValue` in code mirrors the desktop `en/*.json` copy exactly (PARITY is law).
- **Translations live in `mobile/ios/Houston/Localizable.xcstrings`** (one String Catalog,
  en/es/pt). Keys mirror the Swift keypath with a lowercased first segment letter
  (`Strings.Board.columnRunning` → `board.columnRunning`; acronyms fully lowered:
  `AIModels` → `aiModels.*`). Switch-based copy uses one key per case
  (`aiModels.providerDescription.openai`); overloads get suffixed keys
  (`...rateLimitedBodyWithSeconds`).
- **Plurals** use catalog plural variations (`one`/`other`), not `count == 1` ternaries in
  Swift. Interpolations become positional format specifiers in the catalog (`%1$@`, `%lld`).
- **Where a desktop locale key exists, es/pt are the desktop translations verbatim.**
  iOS-only strings follow the same glossary/tone rules as this doc (es tú, pt você, no em
  dashes).
- **Adding a string**: add the member to the right `Strings+<Surface>.swift` with a
  `String(localized:defaultValue:)` call, then add the key to `Localizable.xcstrings` with
  all three languages in the same edit. There is no check-locales script on iOS yet; the
  catalog is the single file to keep complete.
- Language follows the iOS system / per-app language setting (declared via
  `CFBundleLocalizations` in `project.yml`); there is no in-app switcher (Settings is
  pared to Account + Appearance per PARITY-CHAT §7).
